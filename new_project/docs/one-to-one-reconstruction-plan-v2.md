# 一比一复刻重构总计划（Go 后端）

## 0. 目标边界（先定标准，再写代码）

本项目的目标不是“看起来像”，而是“行为一致”。

一比一验收口径固定为四层：

1. 协议层一致：同输入下，返回结构、字段值、错误文案、状态迁移一致。
2. 数据层一致：关键表写入顺序、写入值、事务边界一致。
3. 时序层一致：队列、倒计时、定时完成、战斗推进节奏一致。
4. 视觉交互层一致：登录/注册/玩法窗口状态与关键帧一致。

---

## 1. 技术总架构（保持可替换、可对账）

- 后端：Go（保持 legacy table schema，不先改表）
- 数据库：继续使用旧库结构（`sys_*`、`mem_*`、`cfg_*`）
- 前端：按旧 UI 形态复刻，接口走 Go 适配层
- 兼容层策略：
  - 新接口统一前缀：`/api/legacy/*`
  - 返回中保留 `raw`（旧数组语义）
  - 新增结构化字段（便于现代前端）

---

## 2. 分阶段实施（每阶段都可验收）

## Phase A：账号入口闭环（登录/注册/建角/建城）

目标：跑通“新账号首次进入游戏”完整链路。

- 登录公告、登录、排队检查
- 账号创建（首次登录自动落库）
- 创建角色（用户名/城名/旗帜/性别/头像）
- 创建首城（资源、建筑、新手保护、系统邮件、任务、礼包）

验收：

- 新账号可从未注册状态进入主城
- `sys_user / sys_city / mem_world / sys_sessions` 等关键表对账一致

## Phase B：主城核心玩法闭环

目标：进入主城后核心操作与旧服一致。

- 城池基础信息读取
- 税率/生产比例调整
- 建筑新建/升级/取消
- 科技研究开始/取消
- 征兵开始/取消

验收：

- 同一账号、同一城池、同一操作序列，关键资源与队列变化一致

## Phase C：世界地图与部队

目标：完成“出征-到达-返回”主流程。

- 地图信息读取、目标合法性校验
- 出征、驻防、运输、采集、召回
- 行军时间、负重、粮耗计算复刻

验收：

- 同输入下行军时间与状态流转一致
- 部队表、资源表、告警表写入一致

## Phase D：战斗与战报

目标：战斗结果与战报内容一致。

- 战斗创建与回合推进
- 兵种属性、阵型、技能、伤亡结算
- 战报 HTML 结构与关键字段一致

验收：

- 固定随机种子下结果一致
- 战损/奖励/战报文本一致

## Phase E：外围系统

目标：把“玩法外壳”全部补齐。

- 邮件、任务、联盟、商城、排行榜、好友、活动

验收：

- 每模块至少覆盖：读取、成功写入、失败写入、跨模块副作用

## Phase F：前端一比一与联调收口

目标：最终用户体验与旧版一致。

- 登录、注册、排队、主城、地图、弹窗、战报、邮件等全链路页面复刻
- 1000x600 基准截图与交互状态比对

验收：

- 关键页面截图差异在可控阈值内
- 关键交互（hover/down/on、弹窗层级、按钮时序）一致

---

## 3. 每阶段“完成定义”（DoD）

每阶段必须同时满足：

1. 接口契约文档更新（请求/响应/错误语义）。
2. 冒烟脚本可自动跑通。
3. 关键表对账脚本可复现结果。
4. 至少一组失败路径已验证（不是只测成功路径）。

---

## 4. 风险与控制

- 风险 1：文案与错误码偏差导致“看起来能用，但不是一比一”。
  - 控制：失败路径逐条对齐旧逻辑，维护错误语义清单。
- 风险 2：队列/定时/并发写入导致行为漂移。
  - 控制：关键写路径统一事务，补并发冲突验证脚本。
- 风险 3：前端只做“现代化近似”。
  - 控制：引入截图对比与交互录制作为硬验收项。
